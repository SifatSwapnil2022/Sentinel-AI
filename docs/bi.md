# BI tables

Sentinel publishes the numbers behind the dashboard as seven CSV tables in a star schema, so
they can be loaded into Power BI, Tableau, a spreadsheet or a warehouse. The tables are built by
`sentinel_server.analysis.bi` from the same documents the dashboard reads, so the figures match
the dashboard exactly.

| Where | Address |
| --- | --- |
| Hosted demo | `https://sentinel-ai-sage-gamma.vercel.app/data/bi/<table>.csv` |
| A running API | `GET /v1/export/<table>.csv` (read scope; see [api.md](api.md)) |
| In the repository | `web/public/data/bi/`, regenerated by `make fixtures` |

Conventions: snake_case columns, ISO dates (`2026-10-24`), rates as fractions (`0.7647` is
76.47%), booleans as `true`/`false`, and an empty field for "no value". UTF-8 with a header row,
quoted per RFC 4180.

## Model

```text
              dim_model ─────────┬──────────────┬──────────────┬─────────────┐
              (model_id)         │              │              │             │
                          fact_model_day  fact_feature_day  fact_segment  fact_incident ── fact_incident_signal
                                 │              │                         (incident_id)
              dim_date ──────────┴──────────────┘
              (date)
```

Every fact joins `dim_model` on `model_id`; the daily facts also join `dim_date` on `date`;
`fact_incident_signal` joins `fact_incident` on `incident_id`. All joins are many-to-one.

## Combining rates

Accuracy, label coverage and latency are per model per day. To combine them across models or
days, weight by `predictions`, as the dashboard does: a model with ten times the traffic counts
ten times as much. A plain average of daily rates gives a different, usually misleading, number.
The Power BI measures and the Tableau calculations already do this.

`p95_latency_ms` is each model's own daily 95th percentile. A weighted average of p95s is a
useful trend line but not the fleet's p95; that would need the raw latencies.

## Tables

### dim_model

One row per model.

| Column | Type | Meaning |
| --- | --- | --- |
| model_id | text | Key |
| model_name | text | Display name |
| team | text | Owning team |
| version | text | Model version being monitored |
| description | text | What the model predicts |
| label_delay_days | int | Days until labels are complete |
| reference_rows | int | Size of the labelled reference set |
| reference_accuracy, reference_precision, reference_recall, reference_f1 | rate | Metrics on the reference set, the baseline for "against reference" |
| status | text | `healthy`, `warning` or `critical`, from open incidents |
| open_incidents | int | Incidents open now |

### dim_date

One row per day that has data. `date`, `year`, `month`, `month_name`, `iso_year`, `iso_week`,
`weekday` (1 = Monday) and `weekday_name`.

### fact_model_day

One row per model per day.

| Column | Type | Meaning |
| --- | --- | --- |
| model_id, date | key | |
| predictions | int | Predictions logged that day |
| est_accuracy | rate | Accuracy estimated from calibrated confidence (CBPE), no labels needed |
| est_accuracy_lower, est_accuracy_upper | rate | Likely range of that estimate (3 sampling standard errors) |
| est_precision, est_recall, est_f1 | rate | The other estimated metrics |
| measured_accuracy, measured_precision, measured_recall, measured_f1 | rate | From the labels received so far; empty with no labels. Treat as provisional while `label_coverage` is low |
| label_coverage | rate | Share of that day's predictions with a label so far |
| p95_latency_ms | number | 95th percentile latency logged with the predictions |
| multivariate_error | number | Mean PCA reconstruction error |
| multivariate_upper | number | Top of the expected band for that error |
| multivariate_drifted | bool | Error above the band |
| concept_flag | bool | Measured accuracy over the previous 7 days fell below the estimate's range; empty until enough labels |
| drifted_features | int | Features whose drift test fired that day |
| max_missing_jump | rate | Largest rise of any feature's missing-value share over its reference |

### fact_feature_day

One row per model, feature and day.

| Column | Type | Meaning |
| --- | --- | --- |
| model_id, feature, date | key | |
| kind | text | `numeric`, `categorical` or `binary` |
| method | text | Drift test: `ks`, `chisquare`, `z`, `wasserstein` or `jensenshannon` |
| statistic | number | Test result; a p-value for KS, chi-square and Z, a distance otherwise. Empty when the feature had no values |
| threshold | number | Drift when the p-value is below it, or the distance at or above it |
| drifted | bool | The test fired |
| psi | number | Population stability index against the reference |
| null_rate | rate | Share of rows with no value |
| reference_null_rate | rate | The same share in the reference data |

### fact_segment

One row per model, feature and segment (a category, or a quantile bin of a numeric feature),
comparing the reference with the last 7 days of traffic.

| Column | Type | Meaning |
| --- | --- | --- |
| model_id, feature, segment | key | |
| window_end | date | Last day of the 7-day window |
| rows_reference, rows_current | int | Rows in the segment |
| share_reference, share_current | rate | Share of all rows |
| reference_accuracy | rate | Measured on the labelled reference |
| estimated_accuracy | rate | Estimated for the last 7 days |
| measured_accuracy | rate | Measured for the last 7 days, once the segment has 30 labelled rows |
| labelled_rows | int | Labelled rows in the window |

### fact_incident

One row per incident, open or resolved.

| Column | Type | Meaning |
| --- | --- | --- |
| incident_id | text | Key |
| model_id | text | |
| kind | text | First signal: `concept_drift`, `data_quality`, `estimate_drop`, `multivariate` or `input_drift` |
| title | text | Plain-language name |
| severity | text | `warning` or `critical` |
| status | text | `open` or `resolved` |
| opened_on | date | Second day the rule held |
| resolved_on | date | First of 7 quiet days; empty while open |
| days_open | int | Inclusive, up to today for open incidents |
| metric_basis | text | `measured` (labelled rows only) for concept drift, `estimated` (all rows) otherwise |
| metric_reference, metric_current | rate | Accuracy before and during the incident |
| top_segment | text | The segment that cost the most accuracy, if one stands out |

### fact_incident_signal

One row per signal within an incident: `incident_id`, `kind`, `severity` and `fired_on`.

## Power BI

`bi/powerbi` is a Power BI project (PBIP) with a TMDL semantic model and a report in the PBIR
format. A zipped copy is served from the Reports page.

- Parameters: `DataUrl` (default: the hosted demo's `/data/bi/`) and `ApiKey` (empty for the
  demo; a read key for a live API, sent as a bearer token).
- Relationships as above; `dim_date` is marked as the date table.
- Measures: Predictions, Estimated accuracy, Reference accuracy, Accuracy gap (points),
  Measured accuracy (days at least half labelled), Label coverage, p95 latency (ms), Drift days,
  Largest missing-value rise, Feature drift days, Highest missing rate, Incidents, Open
  incidents, Average days open.
- Pages: Fleet health, Drift and data quality, Incidents.

Open `Sentinel.pbip` in Power BI Desktop with the PBIP and PBIR preview features turned on
(Options, Preview features). The JSON files are checked in CI against Microsoft's published
schemas (`bi/validate_powerbi.py`); TMDL has no schema, so Power BI Desktop is the check for the
semantic model.

## Tableau

`bi/tableau/sentinel.twb` joins `fact_model_day` to `dim_model` and has three sheets (estimated
accuracy by day, accuracy against reference by model, predictions by team) and a dashboard. The
packaged `sentinel.twbx` on the Reports page includes the two CSVs. For the other tables, add
them to the data source from the same folder.

Both are generated by `bi/build_bi.py` rather than saved from the desktop tools, so they stay
reviewable and in step with the table columns. `make fixtures` regenerates them, and CI fails
if the committed files differ from what the script produces.
